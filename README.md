# Spark Streaming: классификация комментариев

> [!CAUTION]
> **🔴 ВАЖНО: УЧЕБНЫЙ ПРОЕКТ.** Используются учебные, демонстрационные или обезличенные данные. Примеры, имена и контакты не следует воспринимать как реальные персональные данные клиентов. Результаты относятся к учебной выборке, а не к действующему бизнесу.

Итоговая работа Simulative: CSV → Kafka → Spark Structured Streaming → Spark ML → минутные окна → memory sink → Pandas/matplotlib.

Основной файл — **`toxic_comments.ipynb`**, с результатами выполненных ячеек. Условие: `ASSIGNMENT.md`.

## Воспроизведение

Нужны Docker Compose, интернет для образов и Maven-коннектора, примерно 3 ГБ свободной памяти для контейнеров.

```bash
python download_data.py
docker compose build
docker compose run --rm notebook
docker compose stop
```

Каждый запуск создаёт новый Kafka topic и checkpoint. Kafka находится только во внутренней сети Docker. Ноутбук автоматически сохраняется вместе с выводом; `evidence/` содержит метрики, оконные счётчики и график. Полные тексты комментариев и модель не публикуются в GitHub, они воспроизводятся из источника.

## Данные и модель

[Google Civil Comments](https://huggingface.co/datasets/google/civil_comments), лицензия CC0. Из original validation-файла после очистки и дедупликации по нормализованному тексту выбираются 6000 train, 1000 validation и 1000 test комментариев. Порядок определяется SHA-256, поэтому разделение стабильно. Это собственный учебный эксперимент, не результат официального benchmark.

Метка токсичности: исходная оценка ≥ 0.5. RegexTokenizer → HashingTF → IDF → LogisticRegression. Обучение IDF и классификатора происходит только на train. В `evidence/metrics.json` есть precision, recall, F1, ROC-AUC, PR-AUC, accuracy и accuracy константного ответа. На validation по F1 токсичного класса выбирается обычная модель или модель с весами классов (веса рассчитаны только по train). Порог 0.5 фиксирован заранее. Итоговая test-выборка не участвует в выборе модели.

В Kafka поступает отдельный CSV с 1000 комментариями и 10 повторными сообщениями. Проверяется, что в итоговой агрегации ровно 1000 записей. Время событий назначено искусственно с шагом в секунду для демонстрации окон.

## Ограничения

Memory sink исчезает при завершении Spark и подходит для учебного анализа. Топик одноразовый, запрос запускается с `AvailableNow`; это настоящий Kafka source, но конечная демонстрация, а не постоянно работающий сервис. Для production нужны долговременный sink, мониторинг, контроль качества входных сообщений и восстановление состояния.

Модель обучена на небольшой выборке, не учитывает полный контекст и не предназначена для автоматических санкций. Её результаты нельзя считать оценкой человека. Улучшение качества и выбор порога потребуют отдельной validation-выборки.

## Полученный результат

На независимых 1000 комментариях: precision **42.9%**, recall **20.0%**, F1 **0.273**, ROC-AUC **0.671**, PR-AUC **0.283**. Accuracy **90.4%**, у константного ответа — **91.0%**. Это показывает, почему одной accuracy недостаточно: модель находит часть токсичных сообщений, но пропускает большинство. На validation вариант с весами оказался лучше обычного по F1 (0.138 против 0.051).

В потоке учтено ровно 1000 уникальных сообщений, 10 повторов удалены.
